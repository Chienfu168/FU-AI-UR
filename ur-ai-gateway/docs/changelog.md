# UR AI Gateway 更新紀錄

本文件記錄 UR AI Gateway 外掛的版本演進、功能新增、架構調整與測試重點。

---

## v1.3.0

更新日期
2026-10-21

版本定位

第二批成本／安全修補的第二部分——授權碼改以「雜湊＋遮罩」儲存（體檢
報告 C1）並加上金鑰輪替（C3）。這是本批唯一會改變營運操作習慣的項目，
已先與服務提供者確認採「建立時顯示一次＋清單遮罩」的做法。

> 報告 C 的第三項「site_url 綁定（C2）」需同步改版客戶端外掛並對既有
> 客戶設緩衝期，已決定延後、另案規劃（見 `docs/security-cost-tracking.md`）。

一、主要變更

1. **授權碼不再以明文存資料庫**（報告 C1）：
   - 新增 `key_hash CHAR(64)` 欄位，存完整金鑰的 SHA-256；查詢（REST
     驗證、後台搜尋）一律改以雜湊比對。金鑰是 40 字元高亂度隨機字串，
     SHA-256 即不可反推，刻意不加 pepper，避免「更換 pepper 會讓所有
     既有客戶金鑰同時失效」的風險。
   - `license_key` 欄位改存「遮罩顯示值」（如 `urg_abcdef...wxyz`，遮去
     30 碼以上），僅供後台清單辨識；並移除其原本的 UNIQUE 索引（遮罩值
     可能重複）。
   - 建立授權碼時，完整金鑰**僅顯示／寄送一次**：手動發放後在後台以
     短時效 transient 顯示一次（不走網址參數，避免進 log），訂閱自動
     開通則於通知信寄出一次。
2. **金鑰輪替**（報告 C3）：後台授權碼清單每列新增「重新產生」按鈕，
   舊金鑰立即失效、產生並顯示一次新金鑰。用於客戶遺失金鑰或疑似外洩時
   重發（因不再存明文，無法「查回」舊金鑰）。
3. **後台搜尋相容**：操作者仍可直接貼上客戶的「完整金鑰」在清單搜尋，
   以雜湊反查命中；一般文字則照常以遮罩值／Email／網址模糊比對。

二、資料庫

- 授權碼表新增 `key_hash`；移除 `license_key` 的 UNIQUE 索引。
- DB 版本 1.1.0 → 1.2.0。`Schema_Manager::install()` 於升級時：dbDelta
  補上 `key_hash` 欄位後，執行一次性遷移 `migrate_to_hashed_keys()`——
  先移除舊 UNIQUE 索引，再以 `SHA2()` 把既有明文算成雜湊、把 `license_key`
  覆寫成遮罩值。遷移具冪等性（條件守衛檢查雜湊是否已填、金鑰長度），
  重複執行不會重複遮罩或污染雜湊。**既有客戶的金鑰在遷移後仍可正常
  使用**（客戶端送同一把金鑰，以雜湊比對命中）。

三、相容性與過渡

- `find_by_key()` 主路徑以雜湊查詢；若遇到「升級瞬間尚未完成遷移」的
  明文列，保留一條過渡相容路徑：允許以明文命中並即時補上雜湊與遮罩，
  確保升級過程中服務不中斷。

四、測試方式

獨立 PHP harness（以 SQLite ＋ wpdb shim 跑真實 Repository）共 21 項檢查
全通過：mask_key／hash_key 格式與 SHA-256 一致性；insert 後資料庫只存
遮罩值＋雜湊（不含明文）；`find_by_key(完整金鑰)` 命中、`find_by_key(遮罩值)`
與錯誤金鑰皆不命中；後台以完整金鑰雜湊反查命中、以 Email 模糊比對命中；
輪替後舊金鑰立即失效、新金鑰可用；遷移條件守衛具冪等性（重跑不改變
雜湊與遮罩）。`php -l` 確認所有變更檔案語法正確。

五、是否建議上正式站

此版會改變營運操作（金鑰只顯示一次、清單只見遮罩），且含一次性資料
遷移。建議：先在測試站以含有既有授權碼的資料庫完整演練一次升級、確認
遷移後既有授權碼仍可連線、手動發放與輪替的「顯示一次」流程正常，再
部署正式站。部署前務必備份資料庫（遷移後明文即不可還原）。

## v1.2.0

更新日期
2026-10-21

版本定位

第二批成本／安全修補的第一部分——端點層濫用防護（體檢報告 D）。純
新增、非破壞性，DB 結構不變（不新增資料表或欄位，升級無需遷移）。

一、主要新增

1. **端點層每 IP 節流**（報告 D，`UR_AI_Gateway_Rate_Limiter`）：在驗證
   授權碼「之前」先用極輕量的計數（WP transient）把同一 IP 的每分鐘
   請求數壓在上限內，超過直接回 429，不進入任何 DB／OpenAI 流程。
   目的是擋掉「大量未帶有效授權碼的洪水請求」，省下資料庫與主機資源。
   - 預設每分鐘 120 次（相當寬鬆；每組授權碼本就各有每日額度，正常
     客戶幾乎不會撞到，此限制主要對付匿名濫用），設定頁可調整，0＝停用。
   - 來源 IP 預設以 `REMOTE_ADDR` 判斷；服務站若在反向代理／CDN 之後，
     可於 `wp-config.php` 定義 `UR_AI_GATEWAY_CLIENT_IP_HEADER`（例如
     `CF-Connecting-IP`）指定要信任的標頭，未定義時不讀任何可被偽造的標頭。

二、測試方式

獨立 PHP harness（以陣列模擬 WP transient）共 8 項檢查全通過：停用（0）
時全放行、無法辨識 IP 時不阻擋、`per_min=5` 時前五次放行第六次起擋、
不同 IP 各自獨立計數、跨分鐘桶重置後重新放行、`get_client_ip()` 正確
讀取 `REMOTE_ADDR` 且非法 IP 回空字串。`php -l` 確認語法正確。

三、是否建議上正式站

非破壞性且預設寬鬆，風險低。若服務站在 CDN／反向代理之後，部署前請
先設好 `UR_AI_GATEWAY_CLIENT_IP_HEADER`，否則所有流量會被視為同一 IP。

## v1.1.0

更新日期
2026-10-21

版本定位

針對一份系統體檢報告中「與線上收費服務（gateway）成本與安全相關」的
高優先項目，做**第一批**修補。這一版只處理「成本防護＋金鑰安全＋
用量可視」四件最急的事，刻意不動任何會改變既有付費客戶行為的部分，
升級後即使服務提供者什麼設定都不改，行為與 v1.0.0 一致（新限制全部
採用寬鬆、非破壞性的預設值）。

> 開發與部署分離：本版只提交到開發分支並附驗證，**是否實際部署到
> 線上 gateway 站（ur-promoter.com）由服務提供者自行決定時機**。

一、主要新增／修補（對應體檢報告項目）

1. **轉發請求成本防護**（報告 A／G，`UR_AI_Gateway_Request_Validator`）：
   在「扣用每日額度之前」先驗證轉發給 OpenAI 的 payload——拒絕串流
   （stream，gateway 無法處理 SSE）、強制 `max_tokens` 上限（取
   `min(客戶端值, 上限)`，未給則補為上限）、限制 messages 筆數與輸入
   總字元數、可選的 model 白名單。無效請求直接退回且**不佔用客戶
   當日額度**。所有上限預設寬鬆（輸出 16384 tokens／100 則／200000
   字元／不限 model），可於設定頁調整。
2. **每日額度原子扣用**（報告 B，`License_Repository::try_consume_daily()`）：
   把原本「讀 → 比較 → 寫」三步分離的額度檢查，改為單一條件式 UPDATE
   一次完成「換日重設＋額度檢查＋遞增」，以受影響列數判斷是否成功
   扣用（0＝已達上限）。避免高併發下多個請求各自讀到舊值、一起衝破
   每日上限的競態問題。
3. **token 用量記錄**（報告 F，新增 `ur_ai_gateway_usage` 資料表與
   `UR_AI_Gateway_Usage_Repository`）：每次成功且含 `usage` 的回應，
   記錄 model／prompt／completion／total tokens 與狀態碼，同時在授權碼
   列累計 `total_tokens`。供日後用量計費、毛利分析與出帳爭議時的依據。
   驗證失敗、額度超限、上游錯誤等「不產生 OpenAI 計費」的情況不寫入。
4. **OpenAI 金鑰可改放 wp-config.php**（報告 E，`Settings::get_openai_api_key()`）：
   優先讀取 `wp-config.php` 的 `UR_AI_GATEWAY_OPENAI_KEY` 常數，金鑰
   不落在資料庫，降低資料庫備份或其他外掛漏洞外洩金鑰的風險；未定義
   時才退回資料庫設定（向下相容）。設定頁會顯示目前金鑰來源。

二、資料庫

- 授權碼表新增 `total_tokens` 欄位；新增 `ur_ai_gateway_usage` 明細表。
- DB 版本 1.0.0 → 1.1.0，`Schema_Manager::install()` 以 `dbDelta`
  同時建立／升級兩張表（既有站台升級會自動補欄位與新表，不需手動介入）。

三、測試方式

獨立 PHP harness（不需 WordPress）共 25 項檢查全部通過：
- 驗證器 17 項：空內容／非 JSON／拒 stream／正常放行且移除 stream 鍵／
  `max_tokens` 壓上限、補預設、保留較小值／model 白名單命中與未命中／
  空白名單放行任意 model／缺 messages／筆數超限／字元數超限（含多段式
  vision content）／`max_output_tokens=0` 時不強制注入。
- 原子扣額度 8 項（以 SQLite 模擬 MySQL 的 `CASE`/`DATE` 條件式 UPDATE
  語意）：`limit=3` 前三次成功、第四五次被擋且計數停在 3、被擋的不計入
  累計；換日自動重設為 1 並更新日期、累計續增；`limit=0` 視為無上限。

`php -l` 確認所有變更檔案語法正確。

四、是否建議上正式站

本批修補皆為非破壞性（寬鬆預設、向下相容），但因 gateway 是線上收費
服務，建議服務提供者在測試站先完整走一次「訂閱 → 授權碼 → 客戶端
代管問答」流程，並：(1) 在 OpenAI 後台設定每月用量上限（硬性成本天花板，
與本外掛的軟性防護互補）；(2) 考慮把 OpenAI 金鑰改以 `wp-config.php`
常數提供後，再正式部署。後續批次（REST 層 IP 節流、授權碼雜湊儲存與
site_url 綁定、金鑰輪替等）見 `docs/security-cost-tracking.md`。

## v1.0.0

更新日期
2026-07-17

版本定位

延續「UR AI Assistant」外掛 v1.31.0 新增的「AI 服務來源」設定（可切換
為「使用代管服務」），這一版建立實際提供代管服務所需要的另一個獨立
外掛——**這個外掛安裝在服務提供者自己的網站（例如 ur-promoter.com），
不安裝在客戶端網站上**。

背景討論：使用者確認未來的免費／付費方向走「服務加值」而非「程式碼
鎖定」（外掛本身維持完全免費開源），並確認由 WooCommerce ＋
WooCommerce Subscriptions ＋ 綠界金流負責訂單與月租收款，這個外掛
負責「訂閱狀態 → 授權碼」與「授權碼 → 實際代理呼叫 OpenAI」這兩段
串接。

一、主要新增

1. **授權碼資料表與服務層**（`UR_AI_Gateway_License_Repository`／
   `UR_AI_Gateway_License_Service`）：每組授權碼記錄客戶 Email、方案、
   來源訂單／訂閱 ID、狀態（啟用中／暫停／已終止／已過期）、每日與
   累計呼叫次數。授權碼字串由本外掛隨機產生（`urg_` 前綴＋40 碼亂數），
   客戶端把它當成 Bearer 憑證使用。
2. **WooCommerce Subscriptions 整合**（`UR_AI_Gateway_WC_Integration`）：
   訂閱進入 `active` 狀態時自動建立授權碼（同一筆訂閱不會重複建立）
   並寄送通知信；訂閱進入其他狀態（`on-hold`／`cancelled`／`expired`
   等）時，依對應表同步更新授權狀態。只在偵測到 WooCommerce
   Subscriptions 已啟用時才掛勾，未安裝時不會出現無意義的錯誤。
3. **REST API 代理端點**（`UR_AI_Gateway_REST_Controller`，路由
   `POST /wp-json/ur-ai-gateway/v1/chat`）：驗證 Bearer 授權碼是否
   存在、狀態是否有效、當日用量是否超過上限，通過後才用**服務提供者
   自己的** OpenAI API Key 真正呼叫 OpenAI，並把 OpenAI 的回應原封
   不動傳回去。刻意維持與 OpenAI 官方 API 完全相同的成功／錯誤 JSON
   格式（錯誤一律是 `{"error":{"message":...,"code":...}}`），讓
   客戶端「UR AI Assistant」外掛既有的 `UR_AI_OpenAI_Client` 解析
   邏輯（`extract_answer()`／`handle_api_error()`）完全不需要修改
   就能相容代管模式。
4. **每日用量上限**：每組授權碼有各自的每日呼叫次數上限（新授權碼
   預設值可在「設定」頁調整），換日時自動重設用量計數，超過上限時
   回傳 429 錯誤。
5. **後台管理頁**：「授權碼管理」頁列出所有授權碼、可手動建立（測試
   或特殊個案用）、可手動調整狀態；「設定」頁填入服務提供者自己的
   OpenAI API Key 與預設每日上限，並顯示完整的 REST 端點網址供複製
   給客戶。

二、設計原則

- 這個外掛完全不處理「收費」本身——訂單、扣款排程、發票都交給
  WooCommerce ＋ WooCommerce Subscriptions ＋ 金流外掛處理；這裡只
  在訂閱狀態變化時做「授權要不要開通」的判斷，職責單純、風險集中
  在單一小範圍。
- REST 端點刻意做成「透明代理」而不是自訂 JSON 契約，讓兩個獨立
  開發的外掛（`ur-ai-assistant` 與 `ur-ai-gateway`）能在完全不修改
  客戶端既有程式碼的情況下互通。
- 規模小、模組少，不採用 `ur-ai-assistant` 那種完整的 Module
  Manager／Bootstrap 架構，直接在主檔案裡依序啟動各服務即可，避免
  為了少數幾個模組另外做一層不必要的抽象。

三、測試方式

1. PHP 整合測試（使用真實 SQLite 資料庫＋真實 `UR_AI_Gateway_
   License_Repository`／`UR_AI_Gateway_License_Service`，非假物件）：
   `create_from_subscription()` 對同一筆訂閱 ID 具備冪等性（不會
   重複建立）；WooCommerce 訂閱狀態正確對應到授權狀態；`is_valid()`
   正確判斷非啟用狀態與已過期兩種情境；每日用量上限正確擋下超額
   呼叫、換日後正確重設；`create_manual()` 可獨立於任何訂閱建立
   授權碼。
2. PHP 整合測試（真實 `UR_AI_Gateway_REST_Controller`，攔截
   `wp_remote_post()`）：缺少／不存在／暫停中授權碼皆正確以
   OpenAI 錯誤格式與正確狀態碼（401）拒絕；正常請求正確用服務
   提供者自己的 Key 轉呼叫 OpenAI 並原封不動回傳結果；OpenAI 回傳
   的錯誤與連線層失敗（`WP_Error`）都正確轉換成乾淨的錯誤回應
   （不會產生未攔截的例外）；每日用量上限在 REST 層同樣正確生效。
3. **跨外掛整合測試**（同時載入 `ur-ai-assistant` 真實的
   `UR_AI_OpenAI_Client`／`UR_AI_Settings` 與 `ur-ai-gateway` 真實的
   `UR_AI_Gateway_REST_Controller`／授權服務，用攔截 `wp_remote_post()`
   模擬 HTTP 往返，把客戶端的請求直接導進代管服務端的 controller，
   再導進模擬的 OpenAI 回應）：確認客戶端切換為「使用代管服務」
   並填入代管服務發放的真實授權碼後，`chat()` 呼叫能完整跑通「客戶端
   → 代管服務 → OpenAI」整條鏈路並取得正確回答；代管服務端把授權碼
   設為「已終止」後，同一個客戶端呼叫會乾淨地失敗並顯示代管服務的
   錯誤訊息，不會發生未攔截的例外。這是這兩個獨立開發的外掛第一次
   真正互相呼叫，也是最重要的一項驗證。

全部情境（授權服務 11 項＋REST 端點 9 項＋跨外掛整合 3 項，共 23 項
檢查點）通過，`php -l` 確認所有新增檔案語法正確。

四、是否建議上正式站

這是全新外掛的第一個版本，建議先在測試環境／測試訂閱方案完整走過
一次「訂閱付款 → 收到授權碼 → 客戶端切換代管模式 → 實際問答」的
完整流程後，再正式對外開放付費訂閱。
