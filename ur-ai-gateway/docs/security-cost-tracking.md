# UR AI Gateway 安全與成本：體檢項目追蹤

本文件追蹤一份 FU-AI-UR 系統體檢報告中，**與線上收費代管服務（gateway）
成本與安全相關**的項目及其處理進度。gateway 是安裝在服務提供站
（ur-promoter.com）、正在線上收費的獨立服務，因此這些項目分批、謹慎處理：
每一批只提交到開發分支並附驗證，**是否實際部署由服務提供者決定時機**。

> 本表的項目代號沿用原體檢報告（A、B、…）。「位置」欄標示該項目主要
> 落在 gateway 外掛，或客戶端 `ur-ai-assistant` 外掛。

狀態圖例：✅ 已完成（在分支上）／🔜 已排入後續批次／💤 待評估／
👤 需服務提供者在外部系統處理。

## 待決策：C 的範圍

C 原本寫成「授權碼雜湊＋site_url 綁定＋金鑰輪替」，但實作時發現這三件
事對線上收費服務的營運面影響不同，需服務提供者拍板：

- **C1 雜湊儲存**：安全效益只有在「不再以明文存授權碼」時才成立。一旦
  不存明文，後台就無法再「重看」既有授權碼（客戶端的金鑰仍可正常運作，
  因為是比對雜湊）。業界標準做法是：建立授權碼時完整顯示一次（請操作者
  當下複製給客戶），清單只顯示遮罩（如 `urg_abcd…wxyz`）。客戶若遺失
  金鑰，改以 C3 輪替重發，而非後台查回。**此為營運習慣的改變，且部署
  後舊明文即消失、不可逆。**
- **C2 site_url 綁定**：要能綁定，客戶端外掛（ur-ai-assistant）必須在
  請求中送出自己的 site_url，但「既有已部署的客戶端」不會送。若直接
  強制綁定會打斷既有付費客戶，需「客戶端改版 → 緩衝期觀察 → 才開啟
  強制」的多步驟流程，且會在兩外掛間建立協定相依。**建議延後，另案
  規劃緩衝期。**
- **C3 金鑰輪替**：後台「重新產生此授權碼」動作，純新增、安全。與 C1
  的顯示 UX 綁在一起最自然。

## 原則備忘

- gateway 與客戶端 `ur-ai-assistant` 兩個外掛**始終保持分離**，不耦合、
  不合併；修 gateway 自身的 bug 不受此限。
- 每一批修補完成後只推到開發分支並附驗證，**部署時機由服務提供者決定**。
- 合併進主幹僅在服務提供者明確指示時才進行。
